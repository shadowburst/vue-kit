# Tier-gated capabilities via Pennant; permissions and features are parallel axes

Tier-gated capabilities are expressed as Laravel Pennant features, scoped to the **Team**. Authorization continues to flow through Policies (per ADR-0002), and a policy method may consult both the user's permissions *and* a Pennant feature when a capability is both role-restricted and tier-restricted. The frontend receives two parallel DTOs — `UserAbilitiesData` (policy results) and `TeamFeaturesData` (Pennant feature values) — so the UI can distinguish "you don't have permission" from "your team needs to upgrade."

## Considered options

- **Fold tier checks into permissions**. Define gates like `reports.advanced` that internally combine `$user->can('reports.view')` with `$team->tier()->atLeast(Tier::Pro)`. Rejected because it conflates two genuinely different concerns: permissions are stable per role and answer "is this role allowed?"; tier is dynamic per subscription state and answers "did this team pay for this?". Folding them muddies error UX (a 403 can't tell you to upgrade) and turns the permission list into a half-truth where some entries are silently tier-conditional.
- **A bespoke `Feature` enum mapping each case to a minimum tier**. Considered as a lightweight alternative to Pennant. Rejected because Pennant already provides the things we'd need to build: scope-based resolution, frontend value dump (`Feature::for($scope)->values()`), and a clean extension path to non-tier-driven flags (early-access cohorts, A/B tests, gradual rollouts).
- **Pennant + dual-DTO** (chosen). Pennant defines features as closures over a Team scope; policies remain the single point that decides authorization but are free to consult features when the capability is tier-gated; frontend gets both axes serialized separately so it can render appropriate UX for each failure mode.

## Why

The user-facing distinction matters: blocked-by-role and blocked-by-tier need different UX. Blocked-by-role is "you can't do this — talk to your team Admin." Blocked-by-tier is "your team needs Pro — upgrade here." Collapsing both into a generic 403 makes the upgrade funnel invisible, which is precisely the funnel a paid product depends on.

At the same time, the *backend* benefits from a single decision point. Two distinct authorization mechanisms (one for permission, one for tier) at every call site is the kind of duplication that drifts. Policies stay the single source of truth; they internally consult both axes when needed. The two DTOs only diverge at the serialization boundary, where the frontend genuinely needs the distinction.

## Consequences

- Pennant is configured with the **`database` driver**. Resolved values are persisted in the `features` table per `(name, scope)` pair. This makes feature checks a single indexed lookup rather than re-running closures on every request, which matters once features start being checked from many call sites per request (policies, Inertia middleware, Vue page props).
- The corollary is that the `WebhookHandled` listener that calls `Feature::for($team)->purge()` on `customer.subscription.*` events is **load-bearing**, not defensive. If it fails, the team's cached feature values go stale and a Pro team appears Free (or vice-versa) until the cache is purged some other way. Treat this listener as critical infrastructure: it must be tested, and any future feature-resolution change that would be invalidated by a state change other than subscription transitions must add to the purge surface.
- **Pennant scope is `Team`**, not `User`. Tier is a property of the team; resolving against the user would force every closure to walk `$user->currentTeam` and handle the null case. The DTO is named `TeamFeaturesData` accordingly.
- `Team::tier(): SubscriptionTier` returns `SubscriptionTier::Free` when `!subscribed('default')`, otherwise resolves the active subscription's `stripe_price` against the `config/billing.php` price→tier map. The `SubscriptionTier` enum exposes `level()`, `atLeast()`, `stripeMonthlyId()`, `stripeYearlyId()`, and `fromStripePriceId()` helpers backed by config.
- Inertia's shared-props middleware nests both DTOs **under the `auth` key**, alongside `auth.user`: `'auth' => ['user' => ..., 'abilities' => fn () => UserAbilitiesData::fromUser($user), 'features' => fn () => TeamFeaturesData::fromTeam($user?->currentTeam)]`. Closures run on full page loads (props always present) and only re-run on partial reloads that resolve the `auth` namespace — giving "always available + on-demand refresh" without the cost of `Inertia::optional()`'s opt-in semantics.
- `UserAbilitiesData` is shaped to mirror the **Policy classes**, not flatten them. One public array field per Policy (`$user` for `UserPolicy`, `$team` for `TeamPolicy`, `$subscription` for `SubscriptionPolicy`), each typed via PHPDoc array shape (`array{viewAny: bool, view: bool, ...}`). Frontend reads `auth.abilities.user.viewAny` as a typed boolean rather than indexing into a string-keyed map. Values are computed via `$user->can('namespace.method')` — one entry per policy method.
- Policies remain permission-only by default. A policy method only consults a Pennant feature when the capability is *both* role-restricted and tier-restricted. Most policies do not change.
- The `RoleName`-style invariant from ADR-0002 still holds: no `hasRole` calls in authorization code. Tier comparisons (`$team->tier()->atLeast(...)`) are not role checks — they're capability checks against subscription state and are permitted in policies.
